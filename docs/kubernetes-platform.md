# Kubernetes platform: plan and decisions

Status: planning, 2026-11-18. Nothing in this document is built yet.

## Why

A permanent Kubernetes cluster inside the homelab, running real applications,
so that keeping it alive is itself the practice. The point is frequent contact
with Kubernetes through operation, not through exercises.

The existing lab cluster (`platform-engineering-labs/k8s/local`) is not moved
here. It is destroyed and a new one is built with the decisions below from day
one. Now is the only moment that is free: no household application depends on
it yet.

That lab repository keeps its role for new experiments: EKS, a throwaway
cluster on VMs, anything that has to be broken on purpose. Its README stays as
the build record of how the first cluster was made, frozen.

## The rule that decides what migrates

**What you use to repair cannot depend on what broke.**

Tailscale is how the house is reached from outside. Pi-hole is its DNS. Komodo
deploys. Dagu runs the backups. Grafana, VictoriaMetrics, Loki, uptime-kuma
and healthchecks are how a failure is noticed. If any of those lived inside
the cluster, a cluster outage would take the repair tools with it.

Those stay in Docker. Not out of caution, out of bootstrap order.

The same rule, learned the hard way, is already in the lab's PM-0006: an alert
path inside the cluster dies with the cluster.

## What runs where

**First wave, stateless, outage tolerable**

`thalesmachado-net`, `it-tools`, `openspeedtest`, `homepage`

They gain something real: automatic certificates, rollout with canary, HPA.

**Second wave, where Kubernetes actually pays**

`vikunja`, `tandoor`, `firefly-iii`

All three use Postgres. CloudNativePG gives them a replicated cluster with
continuous backup, which a loose container does not.

**Never**

Bootstrap and recovery: `tailscale`, `pi-hole`, `nebula-sync`, `keepalived`,
`dockflare`, `cloudflared-agent`, `komodo`, `dagu`.

Observability: `grafana`, `victoriametrics`, `loki`, `uptime-kuma`,
`healthchecks`, `scrutiny`.

Host and hardware: `wolf`, `samba`, `qbittorrent`, `rclone`, `node-exporter`,
`smartctl-exporter`, `cadvisor`.

Special case: `vaultwarden`. Easy to migrate, and it stays. On the day the
cluster breaks and a credential is needed to fix it, the password manager
cannot be inside the cluster.

`immich` and `paperless-ngx` stay for data volume, not for risk.

## Decisions taken, 2026-11-18

**Repository layout.** Split by runtime at the top level: `docker/hosts/` and
`docker/services/` (today's `infra/`), and `k8s/` with `platform/`,
`apps/<category>/`, `charts/` and `gitops/`. Deploy boundary: Komodo owns
`docker/`, Argo CD owns `k8s/`, and the GitHub Actions deploy workflow ignores
`k8s/`.

**Inventory.** A generated table in the README listing every service, its
runtime, its host or `cluster`, and its category. Generated by a script, and
CI fails if the committed table differs from the generated one. A rule that
depends on remembering will drift; a pipeline that refuses the commit will
not.

**Secrets.** SOPS with age. The key lives outside the cluster, so it survives
the rebuild. Sealed Secrets was rejected because its key lives in the cluster.
Vault was rejected as operational weight: a stateful service that needs
unsealing, backup, and becomes another bootstrap dependency.

Docker keeps `.env` on the host as today. Encrypting those into `.env.enc` in
Git is an idea recorded for later, deliberately not bundled with this work.

**Image updates.** Argo CD Image Updater, with `write-back-method: git`, which
needs a write credential and a tag convention. Watchtower does not work for
Kubernetes, and without this the cluster's applications would silently age
while the Docker ones stay current.

**Storage.** Three layers: `local-path` for what rebuilds itself, NFS or SMB
from the NAS through a CSI driver for application data that must survive a
node, and MinIO as S3 for backups.

**Postgres.** One shared CloudNativePG cluster, one database and one role per
application. The trade-off is explicit: shared is simpler to back up and
harder to restore, because a point-in-time restore restores everything.
Recovering one application means restoring to a temporary instance and
extracting that database. That runbook is written before the second wave, not
after the first incident.

**Backup.** The native tools do the work: CloudNativePG writes continuously to
S3, Velero saves objects and volumes to the same S3, a CronJob takes etcd
snapshots. Dagu keeps one job only, reporting failure, through the healthchecks
path that already works.

**Observability.** Nothing new inside the cluster. `vmagent` scrapes and
remote-writes to the existing VictoriaMetrics, Alloy ships logs to the
existing Loki, and alerts stay in the homelab Grafana where they already
reach a phone.

**Ingress.** URLs do not change when an application migrates. Pi-hole keeps the
`*.lan.thalespm.me` wildcard pointing at the homelab Traefik, and each
migrated application gets a specific record pointing at the MetalLB address.
Migration is one DNS line, rollback is deleting it. For public access,
`cloudflared` stays in Docker and its tunnel points at the cluster address.

**Load balancer.** MetalLB in L2 mode. BGP needs a router that speaks it,
Cilium L2 announcements need kube-proxy replacement, and kube-vip does the
same job with fewer users. Revisit if the kernel question below is answered
yes.

**Namespaces.** One per application. The namespace is the unit of RBAC, quota,
NetworkPolicy and deletion, so `kubectl delete ns <app>` uninstalls cleanly.
Category lives as a label and as a folder, which is where it is useful.

**Scheduling.** urahara carries the load: 28 GiB against 7.9 GiB, and NVMe.
zangetsu joins as a light redundancy node. Freeing memory there is not the
answer; not scheduling onto it is.

## Open decisions

**Blocking the build**

The zangetsu kernel. The Raspberry Pi vendor kernel ships no BTF, which is why
the lab could not use kube-proxy replacement (PM-0012), `bpf.masquerade`
(PM-0009) or Cilium L2 announcements. Debian's own arm64 kernel has BTF.
Answering this changes the design of the new cluster, so it is tested before
the platform decisions are finalised, with its own runbook and a rollback that
keeps the current kernel selectable.

Install method and version. kubeadm again keeps the alignment with the CKA.

Single control plane on urahara. Two etcd members are worse than one: a
two-member cluster loses quorum when either one fails.

Pod and Service CIDRs, and the cluster name.

**Not blocking, decided with a date in the platform ADR**

RBAC: a limited user for daily use instead of admin for everything. This is
the largest remaining gap for claiming Kubernetes as a skill.

NetworkPolicy: default-deny per namespace from day one, or later.

Pod Security Standards per namespace. Requests and limits, and whether
`LimitRange` and `ResourceQuota` are set per namespace.

How zangetsu is kept light: a taint with explicit tolerations, which is
honest, or affinity, which is less friction.

## Plan, in order

1. Raise the Grafana container's memory limit. It sits at 414 MiB of 512.
2. Repository reorganisation, in three separate patches: the move with every
   path corrected, the inventory script plus its CI job, and the new README.
   Separate so that a broken deploy points at one of the three.
3. Test Debian's arm64 kernel on zangetsu. Own runbook, own rollback.
4. Write the platform ADR, knowing the answer to step 3.
5. Tear down the lab cluster and build the new one.
6. First application.

## Carried over from the lab

Worth reusing: the Helm chart pattern, the Gateway and HTTPRoute manifests,
the CloudNativePG manifests, and the three probes built on 2026-11-17: one per
hostname, one per node for internet egress, and an alert on etcd WAL fsync
latency. Those three exist because four postmortems happened without them.

Not carried over: the workarounds. The `DOCKER-USER` CIDR script, the
`nodeSelector` pinning cert-manager, the hand-made secrets, the nftables
masquerade rule if the kernel question removes the need for it.

## The safety net

Until the new cluster serves something, every service the house uses stays in
Docker, untouched. If the build fails or stalls, nothing stops working.

That is what makes this low risk, and it is why it has to happen before any
application depends on the cluster.
