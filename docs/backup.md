# Backup: databases and multi-host Restic

## Databases

Every database a service uses (SQLite, Postgres, …) needs a consistent snapshot taken by a script in Dagu, following `sqlite-backup.yaml` / `postgres-backup.yaml`. Restic's hot copy is never enough on its own: a database copied while in use can be corrupt.

- **SQLite**: `scripts/backup/backup-sqlite.sh`, DAG `sqlite-backup` (02:30, zangetsu). Uses SQLite's own `.backup`, writes to `<app>/db-backup/` and keeps the 7 most recent.
  - **Exception, n8n (urahara)**: the first SQLite service outside zangetsu, where a local `docker.run` cannot reach the file. It uses `scripts/backup/backup-n8n-sqlite.sh` plus `scripts/backup/rename-n8n-workflow-backups.sh`, DAG `n8n-backup-urahara` (02:35, `action: ssh.run`, same `\$` escaping and `shell: /bin/sh` quirk as `restic-backup-urahara`), and pings Healthchecks by IP:port (`192.168.15.214:8000`) instead of the container name.
- **Postgres**: `scripts/backup/backup-postgres.sh`, DAG `postgres-backup` (02:35, zangetsu). One `pg_dump` per database; `paperless-db` and `immich-db` on urahara are reached over the network by IP:port, so the DAG does not have to run there. The runner container must be the **same Postgres major as or newer than the newest server in the stack**: `pg_dump` refuses a server newer than the client (`aborting because of server version mismatch`) but reads older servers fine. Confirmed in production: `komodo-postgres` (FerretDB's backend) runs Postgres 17 and a `postgres:16-alpine` runner kept the whole DAG retrying for hours. Bump the runner tag *before* adding a service whose Postgres is newer than it.
- **A new service with its own database** only needs a line in the matching script, never a new DAG. `scripts/backup/restic-excludes.txt` does not need editing either: its patterns are generic (any `.sqlite`/`.sqlite3`/`.db` plus `-wal`/`-shm` sidecars directly under `/opt/apps/<app>/`, and any `/opt/apps/<app>/db/`). Only touch it when the new database falls outside both patterns (an unusual file name, or a Postgres data dir not called `db/`).

Consequence: **n8n workflows are not exported as JSON into the repo.** n8n's `database.sqlite` already holds workflows, credentials and executions and is backed up above, so a parallel JSON copy is redundant and goes stale.

## Restic, multi-host

Filesystem backup of `/opt` and `/etc` with **Restic**, run as a throwaway container started by Dagu (`action: docker.run`, same pattern as the database DAGs). There is no persistent backup app: the DAG, the script and the exclude file are all in git instead of hidden in a web UI.

- **Repository**: a local path on a fixed CIFS mount, `nas-drive/backup/servers/<host>/restic` → `/mnt/backup/<host>`, with the same fixed `.mount` pattern as the media mounts (never `.automount`). `backup/` sits inside the `nas-drive` share (no OneDrive sync), and `servers/<host>/` keeps the homelab hosts apart from the other, unrelated backups stored under `backup/`. There is no remote-storage credential: to Restic this is a local filesystem, so each host's `.env` only needs `RESTIC_PASSWORD` (the repository encryption key).
- **DAGs, zangetsu**: `restic-backup-zangetsu` (02:40, after `sqlite-backup` and `postgres-backup`) and `restic-prune-zangetsu` (Sunday 04:00, `restic forget --prune` with GFS retention: 7 daily, 4 weekly, 6 monthly).
- **DAGs, urahara**: they run on the **same Dagu instance on zangetsu**, but with `action: ssh.run` instead of `docker.run`: the step connects over SSH and runs `docker run` there (`restic-backup-urahara` 02:45, `restic-prune-urahara` 04:30). Dagu cannot point a single *step* at a remote Docker daemon, only the whole process (`DOCKER_HOST` for the entire `dagu` container), which would break the local zangetsu DAGs. `ssh.run` avoids that without a second Dagu instance.
  - A dedicated SSH key (`dagu-restic-urahara`, ed25519) is generated outside the repo, lives in `/opt/apps/dagu/ssh/` on zangetsu (bind-mounted `:ro` into the container at `/opt/homelab-ssh`, never committed) and is authorized for `keydrop` on urahara.
  - The remote `docker run` uses `--network cloudflare-net` (urahara's network: same name, different subnet) and pings Healthchecks by IP:port (`192.168.15.214:8000`, published for this in `healthchecks.yaml`) because container names do not resolve across hosts. That IP also has to be in the Healthchecks `ALLOWED_HOSTS`, or Django answers 400 to any Host header outside the list (seen in production as `HTTP/1.1 400 Bad Request`).
  - **Quirk worth remembering**: `ssh.run` runs `command:` through a real remote shell, unlike a local `docker.run`, which goes straight to the Docker API with no shell in between. It matters because the command is `docker run ... sh -c "… \$var and \$(subshell)"`: unescaped, the **outer remote shell** expands `$envf` and `$(...)` before the container exists, leaving the variable empty (`Fatal: an empty password is not allowed`). It needs `\$` **and** an explicit `shell: /bin/sh` in the step's `with:`; without the explicit shell, Dagu itself strips the `\` before sending the command over SSH, reproducing the same bug. Tested with a throwaway DAG before touching the real ones.
- **Exclude file**: `scripts/backup/restic-excludes.txt`, non-recursive patterns (`/opt/apps/*/*.sqlite`, not `/opt/apps/**/*.sqlite`), so they match only files directly in an app's folder and never the contents of `db-backup/` one level deeper. The database backups themselves are never excluded by accident.
- **Restore**: a standalone container with the same repository mount (`/mnt/backup/<host>:/repo`) and `restic restore latest --target <path>`, or `restic snapshots` to pick a specific point.
- Every host with data to protect needs its own mount and its own pair of DAGs (backup and prune). Never one central repository trying to cover both hosts.
